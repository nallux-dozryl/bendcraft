# Physical inventory key consumer

The normal `remote_resource_presenter` now opts into the AppKit physical-key channel and passes the resulting events through `Presentation.native_events` and `MenuInput.packet_keys`. Hover still comes from actual native Move/Mouse coordinates; a key never invents a hovered slot. Open inventory digits request the existing `MenuClick{slot,Swap{0..8}}`, and physical F requests `Swap{40}`. Closed-world digits retain the ordinary semantic digit event for the existing world selection consumer. Closed-world F does not manufacture an inventory menu or an offhand mutation.

`inventory_key_consumer.Profile` owns nine optional AppKit hardware key codes plus optional offhand, inventory and close bindings. Codes are unsigned16, `None` means unbound, and the presenter rejects malformed profiles before opening a window. Its immutable Config retains the validated profile and the actual native capability through resize, frame, menu and reply continuations. `open_item_table_bindings(...,path,profile)` is the real runtime entry for custom bindings; the existing entry uses defaults. Changing a profile while keys are held requires releasing/resetting input first. A user-facing controls/settings UI and durable binding preference format remain required integration work.

The defaults are physical AppKit positions: digits `[18,19,20,21,23,22,26,28,25]`, F `3`, E `14`, Escape `53`. These names and values were checked against the installed macOS SDK's `HIToolbox/Headers/Events.h` (`kVK_ANSI_*` and `kVK_Escape`). They are a platform namespace, distinct from the Java26.3 receiver's observed digit keys30..38/F9. The existing pinned Java GUI observations in `reference/player_inventory_click_gui.json` remain the independent specification for hovered number/F dispatch, carried-item refusal and missing-hover refusal.

The adapter records identity, pairing, repeat and release; Bend decides bindings and menu behavior. Opt-in events carry `2^31 + hardware`, or `2^31 + 65536 + hardware` when the next queued Key is that physical key's paired logical character. The flag is emitted only when that character is actually queued, including last logical-key release. Duplicate logical holds and batch focus release use the unpaired range. This prevents a physical shortcut on another keyboard layout from also becoming a world key. Search keeps the real character stream while suppressing physical shortcuts; physical Escape exits search. Duplicate bindings use inventory, close, offhand, then hotbar order. Legacy configure-only consumers receive their original logical event stream. Unsupported native channels report False and retain the original packet path.

The actual presenter serializes the resulting typed menu commands through its existing authenticated `call` path. That path admits exact epoch/sequence and clean framing before `MenuInput.completed` installs the complete received snapshot. Pending/latch behavior therefore comes from the production controller. The root's atomic `Wire.Release{}` join remains intact. Capture requests still require a fresh actual native focus status; a late network reply cannot manufacture focus.

Seven new production laws cover complete received MenuSnapshot/catalog retention for arbitrary physical packets, exact legacy fallback, default profile validity, complete-owner physical F routing with paired-character consumption, rebinding, single closed-world digit routing, and search-character retention. They reuse the existing full controller and transfer proof modules. Source typing and independent kernel status are recorded separately in the evidence.
