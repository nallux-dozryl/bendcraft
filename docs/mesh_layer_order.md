The pinned Java 26.3 terrain renderer submits SOLID before CUTOUT. Both use `DepthStencilState.DEFAULT`: the reverse-Z comparison is `GREATER_THAN_OR_EQUAL`, depth writes are enabled, depth bias is zero, blending is disabled, and all RGBA channels are writable. The cutout terrain shader rejects alpha below 0.5. These are actual bytecode and shader-configuration facts; no GPU frame was observed in this investigation.

The configured pipeline therefore allows a surviving cutout fragment at the stored solid depth to replace its color. This conclusion is an inference from submission order, the inclusive depth comparison and disabled blending. The existing Java model fixture reports bit-identical side vertices for grass base and overlay on all four sides. Vertex equality alone does not measure rasterized GPU depth, sampling, projection or final pixels.

The current ray path behaves differently at exact ray-distance equality. `WM.translated` supplies monotonically increasing quad order, and `M.before` chooses the lower supplied order before using source index. The grass base element precedes the side-overlay element, so its opaque fragments win every exact tie even when the overlay passes alpha coverage. The older `test_mesh_render.production_quad` added a cutout priority offset explicitly as fixture policy; that policy is not evidence of production WM behavior or Java submission.

The isolated candidate reserves WM scene order 0..4095 for cutout quads and 4096..8191 for the other quads. WM configuration admits at most 4096 quads. Only exact ray-distance ties use this layer preference; strict nearer/farther comparison remains unchanged. This is a bounded ray approximation of the observed solid/cutout pass ordering. It retains the current within-layer first-order preference and does not claim Java equality semantics within a layer, OIT/translucent parity, quantized depth equivalence, or full raster parity. Translucent consequences remain deferred; the candidate is not installed in production.
